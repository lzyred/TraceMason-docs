01 / 从真实问题出发

任务结束了。
经验却常常没有留下来。

当你长期与 Agent 协作，真正昂贵的可能不是一次回答，而是反复解释同一个约束、纠正同一种偏差。

01

同样的问题，反复纠正

反馈散落在对话里。换一个任务或 Agent，之前说清楚的要求还需要重新解释。

02

记住了，也未必用对

某个项目的临时要求不一定适用于其他任务。经验需要范围、来源和失效条件。

03

规则变多，效果不明

更多提示词会带来额外成本。是否减少错误、是否引入新问题，需要实际比较。

02 / 我们准备怎样解决

从一条反馈，走到一次可验证的改进。

下面是拟验证的产品链路。每一步都需要明确的输入、输出与失败处理。

01 / 理解

还原问题

关联反馈、目标与执行记录，区分事实、个人偏好和项目约束。

02 / 提炼

形成候选经验

写清适用条件、依据与例外，保留来源，允许修正与撤销。

03 / 验证

用新任务比较

比较采用与不采用经验的结果，同时观察改善、退步和额外成本。

04 / 应用

在合适时生效

让 Agent 使用经过验证的经验，记录版本与结果，持续复核。

每次应用，都应能回答：

为什么使用这条经验？适用于什么？依据在哪里？如果错了，如何停用？

03 / 开发方式也是产品的一部分

先证明值得做，
再决定怎么做。

我们把这五个问题作为研发与评审的约束。它们是工作承诺，不是已经完成的研究成果。

  1. 问题是什么？明确用户、场景与不做的范围。
  2. 为什么选这个方案？比较替代方案，包括采用现成工具。
  3. 如何进入整体系统？说明接口、数据权限、依赖与失败处理。
  4. 如何证明有效？预先定义验收方法和停止条件。
  5. 投入是否值得？记录成本与收益，未知数据不填零。
