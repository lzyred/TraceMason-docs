实施批次和验收顺序

P0-1　固定版本与复线路径 · 客户端交付
  1. 从 Build 30 DMG 复制到隔离目录启动，记录包校验、运行进程路径、Build 和服务端镜像。
  2. 用临时身份授权单个账号，分别进入「已保存连接」和「当前配置」；各留一组截图、目录状态码和模型数。
  3. 用另一账号及撤销后的临时身份重复操作。凭据、激活码和请求正文从证据中剔除。
P0-2　贯通两个原生测试入口 · Mini + Server
  1. 复用同一账号解析和目录加载逻辑，设备来源须可追溯至已绑定地址和授权账号。
  2. 目录状态覆盖加载、成功有数据、成功为空、凭据失效、离线、重试。切换账号时丢弃旧请求结果；刷新不覆盖已手填的模型。
  3. 三家分别从列表选择非默认模型，核对 Responses/Messages 请求正文及 Gemini 路径；另测输入目录外的模型 ID。
  4. 通过条件为两个原生入口均能选择和发送，所选模型、实际请求、界面结果三者一致。
P0-3　统一结果含义并定位 Gemini · 网关 + 客户端
  1. 将 HTTP 状态、协议解析、模型正文和预期回复分别记录。覆盖 200 空正文、200 错误载荷、流中断、401、403、404、429、502、超时和取消。
  2. 同一账号、模型和短提示，顺序比较上游原生请求、设备网关请求和真实 CLI；分别核对首包、结束事件、正文和审计状态。
  3. Codex、Claude、Gemini 各留一次可关联的成功样本。上游持续故障时保留最后成功步骤及失败证据，单独标记该账号。
P1-1　安装与配置闭环 · 三套 CLI 适配
  1. 逐一检查可执行路径、安装结果、配置目录和权限。先读出原配置，完成差异预览和脱敏复制。
  2. 在测试目录执行应用、回读、切换和恢复。覆盖用户自定义字段、环境变量凭据、重启和外部编辑冲突。
  3. 三种 CLI 通过正常入口执行，并从原生界面打开同次请求的隐私记录。
P1-2　多工具轮换与撤销 · 身份服务 + Mini
  1. 注入测试时间，验证签发、续领、到期及撤销；一次续领重试得到同一代。
  2. 令一工具忙、一工具空闲、一工具缺失或有配置冲突。记录每个工具的配置代号、验证代号和等待原因。
  3. 在写入、验证、确认三个步骤分别中断并重启；以 Server、磁盘和钥匙串的最终状态核对恢复结果。
P1-3　资料同步、诊断与原型一致性 · Mini
  1. Session 与 Skill 各自执行发现、筛选、预览、同步、冲突、恢复，并验证网关凭据轮换后的独立可用性。
  2. 模拟大量条目；核对加载时窗口响应、筛选、滚动和选择保留。实测耗时后再确定性能目标。
  3. 复核 Debug 可见开关、日志、关闭行为。逐屏核对中文、英文、跟随系统、窄窗口以及错误和空状态。
P2　发布复核 · 安装包与设计记录
  1. 对用户可见的改动先更新版本化 HTML 原型；保留 R9/R10 供逐项对照。
  2. 从最终 DMG 新装及从旧版升级各跑一次 P0 主流程。保留已有配置、历史和配对关系。
  3. 发布记录写明原型修订号、Build、镜像、每种 CLI 版本、通过与失败用例。最终判断依据为安装包实操。

每个验收样本记录什么

入口与构建号 → 工具与授权账号 → 选择的模型 → 实际协议与模型 ID → HTTP 状态与正文验证 → CLI 结果 → 设备代号与请求 ID → 用户看到的状态。涉及配置时附脱敏前后差异及恢复结果。
